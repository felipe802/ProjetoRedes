Race conditions: Como as threads compartilham a mesma memoria, por vezes precisamos de Mutexes (Mutual Exclusion):
Uma thread "tranca" a variável, faz a altereção, e então "destranca". Tal conceito não será necessário nesse projeto.

AF_INET = Address Family Internet. Define a familia de enderecos que sera usado. O sistema de sockets foi criado para aceitar
varios tipos de rede, este especificamente sera IPv4.
SOCK_STREAM é o fluxo continuo de bytes, protocolo TCP e nao UDP
sockaddr_in é a estrutura onde se escreve a porta e o endereco de destino

struct sockaddr_in {
    short           sin_family;        // IPv4
    unsigned        short sin_port;    // A porta (8080) precisa usar htons()
    struct in_addr  sin_addr;          // O endereco IP (ex: INADDR_ANY para qualquer um)
    char            sin_zero[8];       // Preenchimento que mantem o tamanho padrao
}

quando a funcao bind() é chamada, ela espera uma struct sockaddr generica. Usamos sockaddr_in especifica para Internet
e depois fazemos um casting no momento da chamada.

Para receber as mensagens do cliente, podemos usar basicamente duas funcoes: read() é uma funcao generica do Unix/Linux, 
funciona com qualquer file descriptor (arquivos, pipes, sockets, etc), nao possuindo flags especiais. Já recv() funciona 
apenas com sockets, tendo flags especiais como MSG_PEEK (espiar sem remover), MSG_WAITALL (esperar ate receber todos os bytes 
solicitados), MSG_DONTWAIT (operacao nao-bloqueante).

read() e write() ou recv() e send(), estes ultimos propriamente para sockets, com flags.

Erro 56 Transport endpoint is not connected: a licação está sendo encerrada antes que sequer o cliente consiga
enviar alguma mensagem, por isso o recv está la para receber o que o cliente falar.

Erro no bind address already in use: o servidor anterior nao liberou a porta imediatamente. o SO mantem a porta por um tempo
(TIME_WAIT). Esperar até 1 minuto. Para que seja liberado imediatamente usar a funcao setsockopt()

Erro curl 1 received http... not allowed: recebeu algo que nao esta no formato http 1.1, o http 0.9 é obsoleto 
por isso recusado. a mensagem deve ser codificada da maneira adequada para http 1.1

No instante que é executado o comando "curl localhost:8080", o processo do curl faz:
1. Resolução: Ele traduz localhost para 127.0.0.1
2. Socket: Ele cria o próprio socket dele (camada 5 sessao)
3. Connect: ele executa a syscall connect(). Isso dispara o TCP Three-way handshake. enquando o servidor esta travado
no accept(),  o connect() do curl acorda o accept(). assim que o handshake termina, o curl imediatamente chama a funcao
send() no socket dele. entao ele escreve uma string padronizada no buffer de saida da placa de rede. no codigo, essa string 
fica "parada" no buffer do kernel ate que é chamada a funcao recv()

o que o curl envia? seguindo a especificacao HTTP, ele injeta no socket, antes do recv():
GET / HTTP/1.1
Host: localhost:8080
User-Agent: curl/8.5.0
Accept: */*

um novo socket eh criado antes mesmo que o curl seja executado. basta colocar no navegador o endereco.
1. o curl entrega os dados para o kernel do SO
2. o kernel armazena isso em um receive buffer (area de memoria reservada para aquele socket especifico)
3. os dados ficam ali ate que o processo chame recv()

se recv() nunca for chamada, os dados expiram ou a conexao trava. o protocolo http de fato comeca quando 
essa mensagem eh pega do buffer e comecar a tomar decisoes em cima disso.
